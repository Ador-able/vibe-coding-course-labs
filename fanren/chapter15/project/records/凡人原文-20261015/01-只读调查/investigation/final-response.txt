3. **POST 与后续 GET 分别保证什么**

   [store.ts](D:/Projects/Knowledge/.coursebook-work/fanren-ch15-experiments/fanren/chapter15/project/src/store.ts:91) 第91行起在 `BEGIN IMMEDIATE` 事务内核对作品、本章、全部前文修订及大纲范围；第80行起同时更新 `chapters` 并追加 `chapter_versions`。事务提交后 HTTP 才返回 POST 200。

   因此，POST 200表示该请求通过当时的修订检查并完成一次草稿事务：本章修订加一，状态为 `draft`。它不表示页面已经读回，也不表示文学采用。

   随后 GET 返回读取时 Store 可见的作品、完整章节及计算出的 `basisCurrent`。页面只有在两次请求都成功后才删除本地编辑对象、重新显示读回稿。

   这里有明确边界：第18行成功文案使用 POST 的 `saved.revision`，编辑器使用 GET 的 `incoming`；代码没有核对两者标题、正文或修订是否一致。若两次请求之间另一个入口再次保存，显示稿和提示修订可能不同；本轮未实际制造此情形。

   POST 已提交但 GET 失败时，本地对象仍保留，不能反推“服务器一定没保存”。对 `NETWORK_UNCONFIRMED`、`INTERNAL_ERROR`，页面还会设置 `uncertain`，要求先读当前稿。业务预期中的 abort 只针对**服务收到 POST 前**的受控时点。

   第2章修订变化也会令第3章 `basisCurrent=false`，即使第3章正文、修订和历史完全没变。这是前文依据变化，不等于第3章被改写或质量不合格。

4. **`human` 不表示已经采用**

   HTTP 保存入口固定传入 `human`，初始化导入也使用它。它表示保存入口的来源枚举，既不证明身份，也不改变忘语的原作署名。

   `saveDraft` 明确写入 `status:'draft'`、`reviewNote:null`。采用由 `Store.adopt` 第119行起的独立事务执行，另核本章修订并增加修订、写入 `adopted` 和采用说明。任务完成状态则由独立的 `tasks` 表管理。现有初始化记录没有模型任务或采用记录，本轮也没有执行采用。

5. **另一个入口先改本章后，409怎样处理**

   假设本地基于 r1，另一入口先保存到 r2：`saveDraft` 第97行抛出 `STALE_CHAPTER`，HTTP 第31行映射为 409；这次旧基线保存回滚，不新增章节修订。

   页面第7、18行保留 `edits` 中的完整本地标题、正文和旧基线，提示读取当前稿。普通 409不会设置 `uncertain`，所以未经重建基线直接重试仍可能再次409。

   第16行“读取当前稿”在本地仍有修改时：

   - 更新远端 `snapshot`，把当前章放入 `pendingRemote`；
   - 保留上方本地字句及其旧基线；
   - 下方显示远端修订号和只读正文。对照区没有单独显示远端章名。

   [index.html](D:/Projects/Knowledge/.coursebook-work/fanren-ch15-experiments/fanren/chapter15/project/prototype/index.html:18) 第18行提供“以当前稿重新编辑”；其处理在 `app.js:20`，会删除本地编辑对象，再从已读回的 `snapshot` 建立新稿和三类新基线。**它会替换本地标题、正文，没有自动合并，也没有另存被替换本地稿。**需要保留的本地字句应先复制保留，再以当前稿手工合并。

   这些本地字句只保存在页面内存 Map 中；第21行离页提醒不等于持久化备份。

6. **反馈是否清楚，以及一处建议**

   一次200和正文一致，只能支持那次请求及所比较正文的有限结论，不能覆盖标题、等待反馈、POST与GET修订对应、冲突对照、替换本地稿的理解，更不能代替人的内容判断。

   仅建议一处具体改动：把“以当前稿重新编辑”改成 **“放弃本地修改，使用当前已保存稿”**，使文案明确对应现有删除本地对象的行为。本轮没有修改。

   必要验证是：出现409后，读当前稿仍保留完整本地标题和正文；明确点击该按钮才替换本地稿，并取得新的作品、本章、前文基线；随后手工合并不会沿用旧基线。实际文案是否合适、章稿是否采用，仍由人决定。
