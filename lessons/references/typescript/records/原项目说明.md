# TypeScript 与项目运行观察

这个独立命令行练习帮助检查 AI 交来的代码、外部输入、文件结果和运行环境。输入是人工编写的短段落，不是模型生成的新小说。没有模型请求、Agent、界面或生产数据库。

## 固定环境与起点

实际观察环境为 Windows、Node 24.12.0、pnpm 11.20.0；项目依赖固定为 TypeScript 7.0.2、Zod 4.6.5、@types/node 24.19.1。包名为 `ai-runtime-reference`。项目使用 ESM，Node 直接运行可擦除的 TypeScript 语法；静态类型检查另由 `pnpm check` 执行。

`vcr-01-start` 保留实验代码；`vcr-01-complete` 包含同一套代码与本说明。解压下载包后，从解压目录的 `教学记录.bundle` 克隆独立项目；不要在只有源码快照的文件夹中把上层仓库的 HEAD 当作本项目版本。完整恢复命令在解压目录的 `README.md`。

进入克隆项目后依次运行：

```powershell
git rev-parse --show-toplevel
git rev-parse HEAD
node --version
pnpm --version
pnpm install --frozen-lockfile
pnpm check
pnpm observe
```

安装需要访问已配置的包源；后面的观察命令不调用模型或网络服务。pnpm 工作区只包含本项目，避免向上采用另一项目的工作区。其他系统或 Node 版本没有在这次记录中实际运行。

## 观察的内容

`pnpm observe` 依次启动九个真实子进程，保存全部参数、工作目录、标准输出、标准错误和退出码；记录位于新产生的 `runs/<记录标识>/完整观察.json`。观察器完成后退出 0，仍要逐条检查子进程状态。

1. 有效 JSON 输入经过运行时解析，返回完整对象；错误输入的章号是字符串、正文是 null，解析失败且子进程退出 1。
2. 调用 async 保存函数后先看到“函数已经开始”，返回值仍是 Promise；等待写入并全文读回以后才得到文件结果。实际结果在 `output/草稿.json`。
3. 第二次故意把已经存在的 `草稿.json` 文件当作目录，写入其下的 `失败草稿.json`。这次 Windows 运行得到 ENOENT、退出 1；之前那份有效文件全文不变。它不代表覆盖同一路径时发生任何故障都能回滚。
4. 同一环境入口从项目根与 inputs 子目录启动，按工作目录解析的路径变化；按模块位置解析的默认输入路径保持一致。调用者显式传入的相对路径仍按工作目录解析。
5. 观察器先从子环境中删除无凭据的 `VCR01_DEMO_MESSAGE`，再比较未加载文件、显式 `--env-file` 与已有子进程变量优先。它不修改全局环境，也不读取或打印账户密钥。
6. 将“林澈”的六个 UTF-8 字节拆成 1 与 5 字节。各块独立解码产生替换符，持续使用同一个流式 TextDecoder 并结束解码得到完整文字。没有进行 token 切分，也不是模型响应。

## 单项入口

```powershell
pnpm input
pnpm input inputs/错误类型.json
pnpm save
pnpm environment
pnpm encoding
```

有意的失败也会产生错误输出；先核参数、输入与退出码，再判断错误是否符合实验目的。JSON 格式成立和类型成立仍不能证明段落符合人的要求或已经采用。

`output/`、`runs/`、`node_modules/` 是本地运行产物，不提交到项目 Git。下载包的 `原始观察/` 另保留本次自然执行的完整记录和真实保存文件，供不运行命令时阅读。
