:::exercise{title="子流程收到的是哪一批"}
:::question
材料目录有 E02、E01、E03 和 ARCHIVE01 四条。本轮完整输入的 selectedEventIds 只有前三条，tasks 的顺序为 E02、E01、E03。某个方案把子流程的 task 输入写成固定文字“请处理本次读者反馈”，子流程随后读取整个旧反馈库。字段说明写了“本轮选中的任务”，模型也回复“这一批已处理”。你能据此确认三个选中对象完整传入吗？应打开哪些材料，哪些范围仍不能确认？
:::
:::hint{title="说明、值和范围分别看"}
回查完整输入、归档项与字段映射反例。子流程真正收到的 task 是什么？最后条数相同是否足够？
:::
:::answer
不能。字段说明不是 task 对象，固定一句指令没有携带三条完整反馈及稳定身份；读取全库也没有表达这次选中名单的范围。应打开唯一完整输入，再查看拆分、调用节点和子流程入口的全部实际对象，按 eventId 比较完整反馈、读者、作品、章节、批次、资料版本与三项名单。

ARCHIVE01 不在本轮输入。如果它出现在调用或回传里，需要解释范围如何改变，不能继续称为原三项。即使最后恰好有三条，也可能漏一条又重复另一条。这一反例是教师方案，没有执行记录时，只能判断方案信息不足，不能补写本轮实际发生了哪项错误。
:::

:::exercise{title="三个原值，为什么需要三条路径"}
:::question
E01 的 failTask 是布尔 false，E02 是布尔 true，E03 是字符串“false”。规则严格比较原值与布尔 false/true，默认路径为 needs_review。有人说“false 看起来都一样，E03 也按正常任务处理”；另一人说“外层 task 已声明 object，内层就不会有问题”。怎样判断？返回若不按 E02、E01、E03 排列，又怎样对应原材料？
:::
:::hint{title="先看原值，再看身份"}
检查完整 JSON 的引号与外层五字段契约。分类条件检查哪一层？对应结果是否需要依赖数组位置？
:::
:::answer
字符串“false”不能直接当成布尔 false。外层 object 只规定 task 是对象，没有证明内部 failTask 符合业务布尔条件。按本节规则，E01 应去 recorded，E02 应去 classroom_failed，E03 两边都不匹配，应去额外默认输出 needs_review，保留原材料。若业务希望支持类型转换，要另定条件，不在看到结果后偷偷修改本题规则。

返回按 eventId 对应，再核反馈、名单、版本及真实父子执行身份；实际排列另外记录。顺序改变不自动等于丢材料。规则推导与实际发生仍是两项检查，应打开分支输出、完整表行与回传核对。
:::

:::exercise{title="返回了三份回执，哪些还没完成"}
:::question
本节定义中，classroom_failed 和 needs_review 都可以保存回执；recorded 只表示完整课堂回执登记。实际父流程返回 HTTP200 与三份回执，能写“所有任务完成，所有异常都会继续，通知已经送达”吗？再回查已有课堂 E02 的真实失败记录，怎样区分这两种情况？
:::
:::hint{title="回执、异常和外部动作分别找证据"}
看本节三种状态定义，再看旧 E02 的最后节点、真实错误与未出现的成功写入。哪里保存了材料，哪里证明了通知？
:::
:::answer
不能。HTTP200 与三份回执最多证明这个请求返回了这些材料。要逐项按状态定义判断，再独立读回完整表，并核子流程最后输出与父流程接回。classroom_failed、needs_review 没有因为回执保存就变成成功；recorded 不是文学采用。通知是否发生，要看相应外部结果，不能从本题保存推断。

本节分类没有抛出运行时异常，不能证明数据库或外部工具抛错后总会继续。旧 E02 在登记 failed 后，StopAndError 实际产生 NodeOperationError，执行结束为 error，成功反馈写入没有发生，feedbackRowId 为 null。旧 E01 的有效反馈仍在，是另一事件的真实表状态，不证明任意三项同执行都能隔离错误。修复、重试、采用和通知要分别核查。
:::
