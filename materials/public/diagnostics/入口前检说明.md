# 入口前检与实际调用的边界

两次最初前检均在脚本创建模型会话之前退出，没有产生模型调用。以下是当轮工具回执与代码阶段的说明，不把它伪装成另行保存的逐字终端日志；原始工具回执仍在本任务记录中。

第一次：脚本将node_modules/@openai/codex/package.json的非规范符号链接位置直接作为createRequire的基点，查找平台可选包失败。规范解析改用本项目require.resolve('@openai/codex/package.json')后，可以从CLI包的真实依赖位置解析已安装的可选包。这是本练习定位脚本的问题。

第二次：脚本错误拼出vendor/<triple>/codex/codex.exe，用该路径执行--version时前检退出。实际0.160.0平台包使用vendor/<triple>/bin/codex.exe，后续运行采用这个程序的公开codexPathOverride。入口失败时尚未执行startThread/runStreamed。

只读核查还曾因检查脚本使用CommonJS require.resolve去解析SDK的ESM export而退出，随后使用import.meta.resolve。这个检查脚本同样没有调用模型。

完整只读核查见entry-readonly.json。SDK0.160.0的resolveNativePackage本身优先支持bin并兼容旧codex目录；默认new Codex()正确解析实际bin/codex.exe，--version退出0。不能把本练习定位脚本的两个错误说成默认SDK失效或可选包缺失。

四个已冻结模型会话里的Shell失败是另一个阶段：实际回执是Windows sandbox辅助程序启动失败（os error 3），随后的node_repl MCP才完整返回三个课堂文件。检查时所报辅助程序exe本身存在；不声称已定位它启动失败的根因。node_repl来自现有入口工具配置，不是SDK依赖自动提供的读取工具。未修改第三方源码、全局配置或认证信息，也未为诊断补跑模型会话。
