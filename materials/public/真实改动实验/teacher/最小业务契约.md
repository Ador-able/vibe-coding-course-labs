# 本次目标绑定与局部写入的具体契约

## 现有行为与真实缺口

现有 `Store.saveDraft` 将读取当前基线和保存放在同一 `BEGIN IMMEDIATE` 事务，分别检查要求、目标章、全部前章的修订及已传入 taskId 的对象；写当前正文和历史后才提交。现有 CLI 已经有完整要求更新、人工采用、完整导出，HTTP 与 CLI 共用 Store。

现有插件 `binding.json` 只有构建入口与库，`serve.mjs` 没有传 taskId。观察器的 `--chapter` 只写输入记录，不约束 MCP 保存；所以不能拿那条命令中的章号证明写入已经限在这一章。B 使用原 Store 的任务约束并实际绑定 taskId，既有检查得以生效。

现有全章 `save_draft` 也不能保证选区以外的文字原样。C 的目标是一个人真正选中的片段；新动作以这个明确需要为范围，不新增角色、授权策略、审批面板或任务调度。

## 复用任务目标，不制作新状态系统

B 的任务必须在 H1 已经保存第三章大纲之后创建。编者在独立库调用原 `Store.createTask`，完整记录 id、workId、chapterNumber=3、真实 codeVersion 和 created 返回；taskId 由本轮真实 UUID 固定，不从未来事件猜。

准备插件时查原任务，核工作对象和章号，再把 taskId 写到 binding。服务转交给原 `mcp.ts` 的第三个位置参数。原 `saveDraft` 对另一章的合法请求仍会抛 `TASK_MISMATCH`，这需要零模型实际接口验证，不只分析代码。

观察器查绑定目标与命令对象是否一致，沿现有 `src/agent.ts` 在开始、thread.started 和运行结束调用 `Store.updateTask`。沿原已有 created/running/completed/failed/cancelled/interrupted 类型，不新增状态或等待队列。原 SDK 循环、AbortSignal、错误事件与归档方式不变。运行字段与草稿采用分开解释；字段本身不证明任务产物质量。

C 使用另一个指向同一目标章的实际任务记录，不复用 B 的完成任务或覆盖 B 的会话。A 不建写入任务：第三章尚未进入大纲，目标只是提出方案。

## 人实际选定的输入

以下是结构契约，不是本次已经发生的选择；值必须在 H2 完整阅读和真实保存之后取得。

```ts
type ApprovedExcerpt = {
  workId: string;
  chapterNumber: number;
  expectedWorkRevision: number;
  expectedChapterRevision: number;
  expectedPreviousRevisions: {number: number; revision: number}[];
  start: number;
  end: number;
  originalText: string;
};
```

`start/end` 使用现有 textarea 的 UTF-16 下标，指向当前完整正文一个非空连续范围；`originalText` 是该范围实际逐字原文，另存 UTF-8 原件并核 SHA。意见、选择理由、操作者及完整前后文另外完整保存，不把它们复制成第二份当前业务状态。对照当前全文后冻结 JSON/SHA，绑定到本轮服务；服务读取后不随模型的参数改选区。

信任边界用现有 Zod 解析 JSON 的字段类型与范围。内部业务只核对真实对象的动态前提：当前章修订、选区原文是否仍一致，以及原保存函数负责的要求/前文/任务基线。位置在当前正文以外或原文不符时拒绝；不靠截断、相似匹配或猜测寻找新段落。

## 局部入口及共享保存

C 的 MCP 工具集为 `read_work`、`list_chapters`、`read_chapter`、`export_work` 与 `revise_excerpt`。在绑定这份选区的服务进程内，不注册全章 `save_draft`，不是仅在界面藏掉按钮。B 没有局部绑定时仍使用已存在五个整章工具；A 的宿主白名单只允许四个读工具。每轮实际目录须另行确认。

新局部工具只接受：

```json
{"replacement":"人指定范围内的完整替换文本"}
```

使用完整 `z.strictObject` 而不是将它拆成 raw shape，拒绝偷偷夹带 workId、章号、基线或另一段选区。已经阅读本地 MCP SDK 1.31.0 的 `mcp.d.ts` 和 `normalizeObjectSchema`：现有 registerTool 接受完整 schema，Zod v4 对象原样进入解析。正式安装构建和实际非法参数返回仍是后续检查，不能把类型阅读写成运行通过。

共享函数的调用关系为：

```text
实际人工选区 + 模型 replacement
→ MCP 外部 schema
→ Store.reviseExcerpt
→ 读当前目标章并核选区/正文基线
→ 当前前缀 + replacement + 当前后缀，标题取当前标题
→ 原 Store.saveDraft(input, origin, taskId)
→ 原事务及要求/本章/前文/任务对象检查
→ 当前章与历史版本
→ 完整工具返回、read_chapter、HTTP/CLI、五表读回
```

不复制原保存算法，不在 MCP 入口另写数据库。即使读取选区以后被人修改，原 saveDraft 的 expectedChapterRevision 仍在实际事务中检查，拒绝用刚构造的旧正文覆盖新稿；不使用嵌套事务或跨工具锁住全部任务的说法。多个读工具的返回只证明本次取得的对象，整组读取没有一致性快照保证。

新函数返回原 `Chapter` 完整对象，status=draft，历史采用稿保留。它保证选区外内容的构造范围，不保证替换文本在人物、节奏或含义上合格；人的后续完整阅读仍必要。origin 仅表示这次最后写入入口，整章可能同时含已有模型稿与人的有效文字。

## 实际失败分类与范围

旧选区与正文版本用现有 `STALE_CHAPTER`；要求或前章变化沿既有 `STALE_WORK/STALE_PREVIOUS`；选区位置或原文与当前对象不符用明确业务失败。实际返回的错误名、完整参数和对象以运行记录为准，不在设计阶段冒充已经测试。

固定 MCP SDK 的 `setToolRequestHandlers` 会把部分未知工具或参数校验异常包装为 isError 工具结果。因此不预判零模型未知工具请求必然得到 JSON-RPC error，规范的分类和这一固定实现的实际返回分别记。失败后保存前后全五表、完整正文与历史，读回原内容；没有拿报错本身当作原稿一定安全的证据。

受控写入失败只在独立反例库设置 `BEFORE INSERT ON chapter_versions` 的明确教学触发器。让原函数已尝试更新当前章后、保存历史时失败，观察原事务实际回滚。触发器不进入业务实现或正式作品，也不说成正式自然任务遇到故障。

共享业务对象约束不等于系统安全沙箱。沿原 read-only 文件环境与实际工具启用项，核对模型没有直接写库/文件；任务资料与实际缓存绑定分存。这里不制作新的隔离框架或声称排除了全局用户规则。
