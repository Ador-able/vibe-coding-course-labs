:::exercise{title="练习1：摘要结束以后，应该显示什么状态"}
:::question
　　使用前面的完整纪要、正常轮完整两段正文与 62 条原事件。任务是“写摘要，再给 2 至 3 条待确认问题”。同事看到第 32 条 text-end、第 33 条 finish-step，就将整条回复标成已完成，不再接收后续内容。

　　他漏掉了哪项工作？请指出摘要、问题和整条回复各自的真实结束位置。第 61 条进度已写 completed，是否可以单凭它代替第 62 条 finish？本轮完整结束后，摘要是否已经可直接作为忠于原文的纪要？请指认具体原句。
:::
:::answer
　　第 32/33 条只结束 summary 文本和第一步，第 34 条进入 questions，第二次模型请求还包含本轮摘要。问题第 59 条 text-end、第 60 条 finish-step，随后才有应用第 61 条 completed 进度和第 62 条整条 finish。丢掉后续内容就没有任务要求的待确认问题。

　　completed 进度是应用写出的阶段报告，不能普遍替代整个协议的结束或异常边界。这轮最后确有 finish，两阶段完整收到并通过编号检查，仍不认证内容忠于材料。原文是“每次开放预计接待20人”，摘要却说“每次限20人”，增加了硬性上限。问题中的10月10日是新提出的确认建议，不是纪要已确定的日期。使用前要人回查并决定如何纠正。
:::

:::exercise{title="练习2：同一条消息怎样避免重复显示"}
:::question
　　以下文字来自同一份历史：第一行是正常轮第 5、6、7 条 summary 文字增量，第二行是零模型 SDK 读取实际第 4、5、6 个快照的第一段文字投影。

```plaintext
原事件 delta：共享 → 书 → 架
实际消息快照中的文字：共享 → 共享书 → 共享书架
```

　　两种输入分别怎样更新，最后应该显示什么？为什么不能都用“把收到的全文追加到旧内容”？再读第 2、34、61 条 data-progress 和实际完整快照，说明应有几个进度 part，metadata 属于哪里。

　　实际第 57 个快照已有 completed 进度，metadata 仍是 running、stages=[]；第 58 个才更新。能否因前一个标签出现就推断数据库保存成功？
:::
:::answer
　　delta 追加到 summary 对应的文本片段，得到“共享书架”；消息快照采用最新完整值，也得到“共享书架”。重复追加快照全文会得到“共享共享书共享书架”。原片段 ID 用于组装文字，最终消息快照则是页面接收与显示的对象，不能重复累计。

　　三次进度用同一条消息里的 workflow-progress 更新一个 data-progress part。本次 106 个实际快照中最多只有一个进度 part，正常最后为 completed。metadata 放在这条 assistant 消息上，保存型号、应用状态和阶段用量；同名进度 ID 在另一条消息中不表示同一个全局对象。

　　进度和 metadata 由相邻事件先后更新，前一个标签不能证明后一个字段已经变化；本页也没有用这些事件写数据库。持久消息 part 是随消息保留的数据组织方式，不等于已经保存业务对象，更不代表小说被人采用。
:::

:::exercise{title="练习3：有最终对象，为什么仍然没有完成"}
:::question
　　请完整读取停止轮的 52 条原事件、两个阶段及 finalMessage。写出问题阶段全部已收文字、最后三条事件、缺失的结束边界，以及问题用量应怎样表示。

　　SDK 消费者正常读完这份有限历史，最后留下一个对象，可以把它归类为完整回答吗？如果点击回放页“停止回放”，是否等于原模型任务也被新取消了？再次读完整历史能否把它的文字接到旧半句末尾，冒充同一次消息续完？
:::
:::answer
　　实际问题全部为：

```plaintext
1. 志愿者值班名单何时能够确定？是否需要在开放前完成排班并通知相关人员？

2. 与
```

　　第 50 条进度报告 stopped，第 51 条更新 message-metadata，第 52 条 abort。问题没有 text-end、第二次 finish-step，整条没有 finish。摘要为 done，问题为 streaming；问题 finishReason、sdkFinishReason、usage 都是 null，未知不能改成零。

　　消费者正常返回只说明读完提供给它的历史。生产端 onEnd 保存的 finalMessage 也能是未完成材料；没有逐回调参数的日志，就不补写真实 outcome。停止本地回放改变这次 playbackState，不改原 historicalState，也没有新增服务取消；原完整历史即使只读一部分，仍是同一份完整历史原件。

　　再次回放产生新的读取身份，依原事件重建对象，不能把快照全文追加到旧半句。真正重新生成也需要分清新请求的输入、消息和结果归属；本节未实现同会话续写、HTTP 恢复或数据库恢复。先保留旧片段和未完成状态，再依据完整材料决定下一步，不能混出一份看似完整的成功回答。
:::
