# 同一只读任务的五种安排

这个实验帮助我们选择控制方式，不建设小说工作台。它复用最小 Agent 的业务状态与 MCP 服务，模型与工具循环仍由项目固定的 Codex SDK/CLI 承担。

## 运行

把仓库恢复到较短的本地目录，例如 `D:/ai-labs/control-lab`。在本仓库目录，使用 Node.js 24.12.0 或兼容的 Node 24 版本、pnpm 11.20.0，以及前一节已正常使用的宿主登录和模型环境。SDK 与 CLI 固定 0.160.0，MCP SDK 固定 1.31.0，依赖在本项目安装。

```powershell
pnpm install --frozen-lockfile
pnpm build
pnpm test
pnpm compare --case existing --mode agent
```

分别运行 `serial`、`routed`、`concurrent`、`agent` 和 `mixed` 即可比较同一条件。`--case` 可取 `empty`、`existing`、`missing-work`。省略选择或写 `all` 会逐次执行全部三条件与五安排，需要 11 个 SDK 核对轮次；四个作品缺失的应用分支不调用模型。每组新建独立数据库；实际 Agent 是否额外读取由当次事件决定，不保证工具数相同。

本程序沿用正常宿主环境，不改 HOME、CODEX_HOME、全局设置或个人记忆。默认不指定模型；可通过项目本地 `lab.config.json` 的 `model` 或 `codexPathOverride` 显式选择，配置与实际选择保存在本次输入和条件中，不放认证内容。公共事件没有报告具体模型名时，不依据默认值猜测。动态安排以 `enabled_tools` 将 novel_lab 业务工具限制为 `read_work`、`read_chapter`、`list_chapters`；其他宿主配置仍被继承，是否执行了其他动作需看实际公共事件。本实验提示明确要求仅做这些业务读取。

若工具发现前辅助宿主启动失败，先保留本次记录，不把最终回答的“完成”当作工具成功。一次 Windows 对照中，同字节的 0.160.0 辅助程序在 270 字符路径下没有实际读取事件，在较短入口下取得了所需材料；这不证明所有此类错误都由路径长度引起。可使用较短恢复目录，或在 `lab.config.json` 用 `codexPathOverride` 指定已经核对版本和字节的官方 0.160.0 `codex.exe` 短路径。不要用可能来自全局的 `pnpm exec codex --version` 代替 SDK 实际启动路径的核查，也不需要更改认证、只读沙箱或全局设置。

## 固定目标和数据

只读核对第 1 章：已有正文时对照确认事实与章目标，没有章稿时给准备方向和仍需人判断的事项，读取失败时准确报告；不创作完整章节、不保存、不采用。

- `empty`：初始化作品《乌桐镇的停钟》，第 1 章尚无章稿。读取成功的 `null` 表示这一状态。
- `existing`：同一作品中，由人工载入 `evidence/01-单章真实运行/完整运行-chapter.json` 的完整正文。这个文件来自 2026-10-02 前一节真实 Agent 保存的草稿；当前数据库的 human 来源表示本次载入动作，不表示该正文由人创作。仍为草稿，未采用。每组载入时刻不同，正文、要求、事实与修订条件相同。
- `missing-work`：同一初始化数据库，任务目标指定为不存在的 `absent-work`，观察 `WORK_NOT_FOUND`。这不是章稿为空。

## 控制顺序

`serial`：应用先读作品、再读章稿，将完整结果提供给 SDK 作核对。首项读取失败则止步。

`routed`：应用先读章稿。错误止步；正常返回 null 则进入准备分支；正常返回正文则进入核对分支。两种有效分支都再读作品要求。这里是明确业务状态分支，没有另加模型分类请求。

`concurrent`：应用同时启动两项独立只读 MCP 请求，逐项保留成功、失败及原始返回，汇合后再核对。它们没有相互输入依赖；本服务使用同步 SQLite，两个 Promise 同时在途不证明服务端计算同时进行。不人为延迟、不以单次速度排名。

`agent`：应用不预读材料，由成熟 Harness 中的模型选择可用业务工具，接收真实反馈，再判断下一步。它也可能选择同时读取，本次记录确实如此。程序没有自制模型工具循环。

`mixed`：应用固定读取并核实作品。失败则止步；成功后把要求完整提供给 Agent，由它补查章稿和判断是否还需要别的读取。

## 看什么记录

每次执行在 `runs/control/时间-标识/条件-安排/` 保存：

- `input.json`：本次完整提示、实际作品标识与应用已读取资料。
- `app-reads.jsonl`：应用启动和结束的每一项 MCP 读取，成功结果、错误和原始返回。
- `sdk-events.jsonl`：若启动 SDK，保存全部公共事件，包括实际工具动作、消息和整轮用量。
- `baseline.json`、`after.json`：前后作品与章稿完整状态，正文与修订均可核对。
- `report.json`、`final-response.txt`：会话运行、实际材料和最终回答分别记录。应用发现业务错误时无需再让 AI 翻译同一错误；仍保留原始错误。中断或失败的结果也保留。

`appReadCalls` 是应用业务读取数，`modelToolCalls` 是 SDK 公共事件中的 MCP 调用数，`sdkTurns` 是本程序调用 runStreamed 的轮数。这些都不是底层模型请求次数。usage 为 SDK 整轮汇总，缓存和输出也各自记录，不据此编造账单或推断稳定耗时。

`sdkState` 表示 SDK 会话是否结束；`materials.ready` 依据应用读取和实际 SDK 业务工具结果，检查作品要求与目标章稿是否都已取得。目录、最终文字或别章读取不代替第一章的完整结果。成功的 null 才表示空稿。材料齐全仍不证明引用和判断正确，需要人核对正文。没有取得完整材料、会话没有正常结束或业务内容改变时，命令返回非零退出码；记录仍然保存。因此 `missing-work` 的预期止步也会返回非零，它不是成功核对目标作品。

`evidence/04-控制方式对照/` 保留作者 15 次原始记录，记录注明的运行代码提交为 41d8550。它们使用当时的 `state` 字段，仅表示会话或应用止步状态；不可把历史字段解释成当前的材料验证。记录以当次实际代码和条件为准。只有阅读原文才能判断引用是否成立、建议是否适当；完成状态不能替代内容判断。
