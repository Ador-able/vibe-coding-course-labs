# 四题完整提示与答案

## 1. 文件事件为绿色，AI却讲了另一本书

问题：文件触发器返回一条资料：`id="drive-file-123"`、`name="第三章资料.pdf"`、`mimeType="application/pdf"`。下一节点把整个对象写进提示，AI给了流畅摘要。你能认为AI已读到这份文件吗？按顺序列出还要检查什么。这里的ID是题面假设，不是课堂已连接的真实Google对象。

提示：先指出当前对象中哪一项是正文；再区分取得文件与解析文件两步。

答案：不能。现有对象只有身份和类型等元数据，没有PDF字节，也没有提取文字。先确认当前授权账户能否下载这份对象；普通blob要核真实下载响应，Google Workspace原生文档要核正确导出入口与格式。再查实际二进制字段、字节与MIME，交对应解析器并读完整文字。最后核真正给模型的消息是否含这份文字，而不是目录对象或base64。流畅摘要只说明模型生成了话，不能替代上述证据；即使文字成功进入请求，摘要是否忠于原文仍需回查。

## 2. 同一语音链有两次报错

问题：上传节点的文件放在binary.audio，转写节点仍找binary.data；改好后转写返回`text="请说明两加二是多少"`，文字助手还从旧聊天触发器读chatInput。两次错误分别发生在哪里？只把所有字段统一叫data是否足够？

提示：先给两个边界分别标出输入类型，再看旧聊天节点是否仍在当前路线中。

答案：第一次是二进制入口名称失配，应让转写节点读取实际audio字段，或明确调整上游输出后逐字节核。第二次是转写文字到助手的映射失配，应读取本次转写节点真实text，而不是已被替换的聊天触发器或空chatInput。统一叫data不能自动解决节点归属和数据类型：audio文件字节与text字符串仍是不同对象。再检查模型实际收到的文字、合成文件、HTTP返回和实际播放。原课最终听到回答只证明当次链路，不证明正式发布和跨会话记忆已完成。

## 3. 下载成功却提取不到文字

问题：一个三页PDF下载返回成功且有字节；解析节点没有得到可读文字。操作者提议把文件名写给AI，让它依据常识补一份说明。应该怎样处理？如果本节已有文字型PDF解析成功，能否说扫描件也已通过？

提示：把下载正确、解析能力与补写内容分成三项判断。

答案：先保留真实字节和解析的空结果或错误，确认选中的binary字段与格式，再查看原PDF是否有可提取文字、是否主要是扫描图像或存在其他解析条件。需要OCR或多模态读取时采用确实可用的入口，再逐页核取得的文字与原页；没有这一步就保持“未取得可用正文”，不生成虚假的完成稿。文件名只能帮助定位，不能补出文件内容。本节文字型PDF的一次成功不外推为扫描OCR、复杂表格和全部格式可靠，且不能把原05-01/PyMuPDF结果冒充本次n8n结果。

## 4. 两路都完成，最后只剩第一份材料

问题：同一次目录输入有PDF和TXT两项，两路各成功。合并时把所有资料的sourceId与正文都取自某节点的第一项，返回里出现两条完全相同记录。如何定位？如果希望后续加入文件夹自动触发，还缺什么证据？

提示：沿每条记录检查“自己的编号—自己的binary—自己的text”；不要从最终行数直接判断关联正确。

答案：回读拆分后的两项身份、真实下载结果、解析节点输出与分支合并，检查是否误用`.first()`或第一项映射，造成第二份材料被覆盖。两条记录不等于两份材料都被正确传递；需要保留各自关联和完整文字，核最终消息逐项填入自己的text。加入自动触发前，先保留这个有限手动基线，再核正式发布、轮询或回调条件、真实事件与重复流程。文件夹暂时没有匹配事件不必然是故障；一分钟轮询不能说成即时推送；原课双通知由旧流程同时启用造成，不能自动归因于解析节点重试。
